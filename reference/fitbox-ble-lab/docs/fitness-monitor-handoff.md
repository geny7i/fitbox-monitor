# FITBOXエクササイズモニタ：新プロジェクトへの引き継ぎ

作成日：2026-10-23。新しい実装担当者が、このドキュメントと同梱の検証コード・ログから開発を始めるための資料。

## 1. 今回作るもの

**FITBOXのBLEケイデンスセンサーを入力にして、一般的なフィットネスバイクのモニタのように使えるブラウザアプリを作る。** 対象はまずMacのChrome。

ユーザーが望んでいること：

- 運動中に回転数・時間などを読み取りやすく表示する。
- このセンサーで実際に取得できる範囲を中心に機能を組み立てる。
- 想定されるペダルの回転をグラフィカルに表示し、実物と見比べながら補正を感覚的に調整できるようにする。
- 今の検証プロジェクトを新アプリのプロジェクト内へ置き、参考資料として使って実装する。

地図・Street View・街の自由走行の構想は保留。今回の開発範囲に含めない。`virtual-cycling-feasibility.md`は過去の検討資料。

以下の画面・計算方法・構成は、これまでの測定を踏まえた**実装案**。ユーザーが確定した細部と混同せず、通常の実装判断で調整してよい。

## 4. センサー分析で引き継ぐ重要事項

ユーザーが「約100秒かけて100回転」させた2件の実測ログがある。reverseは**センサーの取り付け反転**であり、ペダルの逆回しを検証したものではない。

| 観測 | forward | reverse |
| --- | ---: | ---: |
| 通知数 | 203 | 213 |
| Crank累積増分 | 204 | 202 |
| Crank増分×0.5 | 102回 | 101回 |
| Wheel累積増分 | 641 | 634 |
| Wheel増分 / Crank増分 | 約3.1422 | 約3.1386 |
| センサー時刻 / PC時刻の進行比（初動を除く） | 約1.9578 | 約1.9551 |

全416件の生HEXと解析済みフィールドの一致を確認済み。以下を実装の前提とする。

1. **生のCrankカウンターをそのままペダル回転数にしない。** この個体の初期仮補正は`0.5`倍。正確に100へ合わせるために102や101を機械的に割り直さない。開始停止の余分な回転などが区別できていない。
2. **標準式で計算済みのrpmを、さらに単純に0.5倍しない。** カウンターとセンサー時刻の両方が約2倍に進むため、標準式のrpmはおおむね60前後となる。
3. **Wheelは独立した測定量として扱わない。** Crankの約3.14倍で、全通知で時刻も一致。仮想値の可能性が高いが生成方法は未確定。
4. **2件の通知を無条件に重複削除しない。** 短時間に2件ずつ来るがHEX・カウンター・時刻がそれぞれ進んでいる。通知間隔だけで回転数を求めない。
5. 累積回転カウンターとセンサー時刻には桁あふれがある。Crankは16ビット、Wheelは32ビット、時刻は16ビット。標準CSCの時刻単位は1/1024秒だが、この実機の時計の挙動は標準どおりと仮定しすぎない。
6. 約1000Hzでの時刻生成等は仮説。ファームウェア不具合・製品一般の仕様とは断定しない。個体別の補正として保存する。

### 表示上の既知の不満

ユーザーは10回転ずつ目視確認しようとしたが、表示がちらつき、停止後に出力が消えて確認しづらかった。既存アプリは通知ごとの増分表示と、回転更新から5秒で瞬間rpmを空欄にする動作を持つ。

**新アプリでは総回転数・経過時間・平均値・直近の計測結果を停止後も保持する。** 停止時に変えるのは現在rpmと状態表示。通知がなくなったことと、結果を消すことを結び付けない。

## 6. 回転を見ながら補正する画面

### 体験の提案

1. 「回転の補正」を開き、実物を見やすい位置にMacを置く。
2. 画面にクランクと左右のペダルを側面図として大きく表示する。片方のペダルに色を付け、**色付きのペダルが一周すると1回転**と分かるようにする。
3. 実際にこぐと、現在の補正値で推定した速さで回る。
4. 「画面が実物より速い → 遅くする」「画面が実物より遅い → 速くする」で調整する。スライダーと数値欄も用意する。
5. 補正前後の推定rpmと、補正画面での回転合計を固定位置に表示する。止めた後も合計を残す。
6. 「この補正を使う」で保存。キャンセルでは既存設定を維持する。初期仮設定（0.5倍）に戻す操作も用意する。

**目的は回転の速さを合わせること。実物のペダル角度と画面の角度が一致するとは保証しない。** 今のログには絶対角度がなく、遅延やまとめて届く通知もある。見た目の方向も表示用の設定であり、センサーから回転方向を取得したと表示しない。

画面の一周が何回転か分からなくならないよう、回転方向の印・色付きペダル・固定した基準点を使う。既定は60rpmで毎秒一周となる。必要なら「位相を合わせる」操作で描画の角度だけをリセットできるが、回転数補正とは分ける。

### 補正パラメーターの意味

内部では`pedalRevolutionsPerRawCrank`など意味の明確な名前を使う。

```text
補正後の回転増分 = 生Crankの増分 × 補正倍率
初期の仮倍率 = 0.5
例：生Crankが20増えたとき、0.5倍ならペダル10回転
```

単に「補正倍率」と表示するなら、この意味を短い例で説明する。「2倍」という表記がカウンターの割り数なのか回転速度の倍率なのか曖昧にならないようにする。

調整範囲は仮に0.1〜2.0、0.01刻み＋数値入力とする。範囲は製品仕様ではなくUIの提案。「遅くする」で倍率が減り、「速くする」で増えることを統一する。診断用の標準式rpmへ、この倍率を重ね掛けしない。

感覚調整には誤差があるので、任意の補助として「手で数えた回転数」を入力できる方式もある。例えば生Crankが40増えて実際20回なら倍率は20÷40＝0.5。この方式でも最初の基準値を取得してから回し、停止後に結果を確かめられるようにする。

### アニメーションの実装条件

- 通知が来た瞬間にペダルを跳ばす描画にはしない。安定化した推定rpmを使い、`requestAnimationFrame`等で連続描画する。
- 角度は `角度 += rpm × 360 / 60 × 経過秒`。描画用の積分値を総回転数として記録しない。
- 回転合計は生カウンターの差から集計し、描画とは独立させる。
- 停止・切断・一時停止で回転表示も止める。再開時や背景タブから復帰したときに一気に回転させない。
- 補正プレビューと通常モニタで同じ補正・rpm計算を使う。見た目だけ変わって記録が変わらない不整合を作らない。
- 補正中は通常の運動セッションを開始しないか、一時停止する。設定変更は次のセッションへ適用し、終了済みの記録を黙って再計算しない。

## 7. 回転数・時間の計算方針

### 推奨する初期案

補正済みCrank増分とPC側の経過時間を共通の土台にする。これなら補正画面で倍率を調整したとき、回転合計と推定rpmが同じ方向に変化する。

```text
counterDelta = (currentCrank - previousCrank + 65536) % 65536
pedalDelta = counterDelta × calibrationFactor
currentRpm ≈ 直近の時間窓内のpedalDeltaの合計 × 60 / 窓の経過秒
averageRpm = セッションの補正後回転数 × 60 / セッション運動時間_秒
```

通知が2件近接するため、隣接するPC受信時刻だけで瞬間rpmを計算すると極端な値になる。数秒の時間窓（初期案3〜5秒）で集計して平滑化し、起動直後や十分なデータがないときは「計測中」と表示する。平滑化には表示の遅れが生じるので、実機で安定性とのバランスを決める。

セッション内の時間計測には単調増加する時計を使う。保存・ログの日時にはISO時刻を使い、記録再生ではログの受信時刻差を再現する。一定周期で届くと仮定しない。

標準CSC式のrpmも比較・診断用に残せる。将来こちらを主表示に採用する場合は、回転合計の0.5倍補正とは別の換算設計が必要。今回の実測だけで時計単位の固定補正を導入しない。

### 状態と例外

| 状況 | 推奨動作 |
| --- | --- |
| 初回接続・再接続 | 最初の通知は基準値。過去の累積値をセッションへ加算しない |
| 同じカウンターの通知 | 新しい回転として数えない。通信が続いていることは別に記録 |
| 停止・長い更新間隔 | 現在rpmを0または更新なしに移行し、合計と結果は保持 |
| 一時停止中 | 運動時間・回転合計へ加算しない。受信基準は更新するか再開時に再取得し、停止中の差分を取り込まない |
| BLE切断 | 計測を自動的に一時停止。復帰時に切断中の回転をまとめて加算しない |
| 桁あふれ | 通常の周回を補正。機器のリセットを巨大な回転増分と誤認しない |
| 不正・不連続データ | 診断へ記録し、妥当な次の値で再基準化する |
| 背景タブ・スリープ | 動作継続を仮定せず、復帰時に間隔を確認。不明区間は一時停止扱いにできるようにする |

初期版の時間は「開始〜一時停止／終了までのPC経過時間」とし、ユーザーが回転を止めただけではタイマーを止めない案。平均rpmもこの時間を分母にする。自動停止時間を除いた「実際にこいだ時間」を追加する場合は別指標として定義する。

未更新タイムアウトは仮に5秒から試し、低速試験で調整する。「動いていない」「回転通知がない」「BLEが切れた」は同一ではない。タイムアウトの判定は新しい回転が検出された時刻と最後の受信時刻を分けて行う。

## 8. 実装構成の案

新アプリはTypeScript＋Viteを基本案とし、UIが増えるならReactを使う。既存の検証アプリはビルド不要のJavaScriptで、フレームワーク採用はユーザーの確定指定ではない。初期版は静的配信とブラウザ内保存で成立する構成を目指す。

処理は次の単位に分けると、実機がなくても検証しやすい。

```text
BLE通知 または 実測ログ再生
  → CSC生データ解析
  → カウンター差分・不連続の判定
  → 個体別補正
  → セッション集計・rpm推定
  → モニタUI / 回転アニメーション / 記録保存
```

BLE入力とログ再生を同じ計測処理へ渡す。再生は明確に「記録の再生」と表示し、実機の値に混ぜない。ログの`rpm`・`total`は旧アプリの計算結果なので、新アプリの回帰検証ではHEXと受信時刻から再計算する。

保存するセッションには、補正倍率・計算方式のバージョン・使用デバイス・開始終了時刻・一時停止情報・結果を含める。校正設定はデバイスのブラウザ内識別子等に関連付け、名前だけで別個体へ無条件適用しない。JSON出力には仕様バージョンを付ける。

## 9. 検証・受け入れ条件

### 実機なしで確認すること

- 既存CSCテストの内容（両フィールド、桁あふれ、短いパケット）を引き継ぐ。
- 生ログを再生すると、forwardの生Crank増分204／reverseの202を再現できる。
- 0.5倍設定なら102回／101回。ユーザー申告に合わせてちょうど100回になるテストにしない。
- 近接する2件を取り込んでもrpmが数千などに跳ねず、平均が約60rpmの運動と整合する。
- 同じHEXの再受信で回転合計が増えず、再接続・一時停止・終了後に不正な加算をしない。
- 補正を0.5→1.0に変えると、同じ記録のプレビューrpm・回転合計が2倍になる。標準式rpmの二重補正がない。
- 既知の60rpm入力に対して、描画は毎秒一周する。描画を止めても保存結果を失わない。

### 実機で確認すること

- Mac Chromeで接続・切断・再接続ができる。
- 通常の運動中に数字が読め、停止後に総回転数と結果を落ち着いて確認できる。
- 補正画面の「遅く／速く」が直感どおり動き、保存した設定が再起動後も復元される。
- 20回転程度を手で数え、低速・通常・速めで図と実物の速さを比べられる。
- 停止、ゆっくり再開、切断、一時停止中の回転で不自然な回転数の飛びがない。
