# FITBOX-03807：取り付け方向と回転ログの分析

分析日：2026-10-23。ユーザー申告は「約100秒でペダルを100回転」、reverseはセンサーの取り付けを逆にした試行。逆回しした試行とは解釈していない。

## 結論

- **今回の約60rpmの試行では、取り付けを反転しても同様に測れている。** どちらか一方だけを正しい向きと判定する根拠はない。
- **Crankの累積増分は実際の回転数の約2倍。** 仮に2で割るとforwardは102回、reverseは101回となり、申告の100回に近い。
- **WheelはCrankの約3.14倍で、両者の最終回転時刻は全通知で一致。** 独立した車輪測定より、同じ入力から生成した仮想車輪値という仮説が有力。
- **累積値だけでなくセンサー時刻にも特徴がある。** 単純に表示rpmを2で割る補正は不適切。

向きの比較は各1試行のみ。低速・高速・短時間の始動、長時間の安定性、メーカー指定の取り付け向きまでは判定できない。

## 入力と検証方法

- [forwardログ](fitbox-2026-10-22T15-50-25-441Z.forward.json)
- [reverseログ](fitbox-2026-10-22T15-54-02-865Z.reverse.json)
- [再実行用スクリプト](../scripts/analyze-fitbox-logs.mjs)：プロジェクト直下で `node scripts/analyze-fitbox-logs.mjs`

保存されたHEXを既存のCSCパーサーで再解析し、全416件のWheel / Crankカウンター・時刻・flagsがログの解析済みフィールドと一致することを確認した。集計は画面のrpm表示だけに依存せず、最初と最後の生カウンターから求めた。

## 比較結果

| 指標 | forward | reverse |
| --- | ---: | ---: |
| 最初〜最後の通知の時間 | 104.008秒 | 111.061秒 |
| 通知件数 | 203 | 213 |
| 値が変化した通知件数 | 196 | 202 |
| 値が変化しない通知件数（初回を除く） | 6 | 10 |
| Crankの開始値 → 終了値 | 480 → 684 | 712 → 914 |
| Crank増分 | **204** | **202** |
| Wheelの開始値 → 終了値 | 1507 → 2148 | 2236 → 2870 |
| Wheel増分 | 641 | 634 |
| Wheel増分 / Crank増分 | 3.1422 | 3.1386 |
| Crank増分 / 2（仮補正） | **102回** | **101回** |

記録時間には運動前後の停止も含まれるため、通知の全時間をそのまま100回転の所要時間とみなさない。forwardとreverseの1〜2回程度の差は、開始・終了時の余分な動き、手で数えた回数、検出の誤差などを区別できない。方向による精度差と断定するには足りない。

## 2件ずつ増える特徴

値が変化する通知を順に並べると、2件ずつのペアで時刻増分とCrank増分が一致した。

| 指標 | forward | reverse |
| --- | ---: | ---: |
| 連続する変化通知を2件ずつ組にした数 | 98組 | 101組 |
| 組内でセンサー時刻の増分が等しい | 98/98組 | 101/101組 |
| 組内でCrank増分が等しい | 98/98組 | 101/101組 |
| 組内の受信時刻の差の最大値 | 約61ms | 約120ms |

例：forwardの15:48:45.712Z付近では、同時刻にCrankが484→485→486と増え、センサー時刻も36440→37360→38280と920ずつ増えている。reverseにも同じ構造がある。

これは「同一パケットを2回受信した」だけではない。**2件のHEX自体が違い、それぞれカウンターとセンサー時刻が進んでいる。** ログの合計を計算するときに同じレコードを誤って足したという説明ではない。

センサー側のデータ生成処理等で、1回の検出に対して2回値を進めている可能性がある。ただし、デバイス内部・通信経路・ブラウザを切り分ける計測はしていないため、ファームウェアの不具合と断定はしない。nRF Connectで同様の生データを記録すれば、ブラウザ以外でも再現するか比較できる。

一部のforward通知はCrankが2ずつ増える。累積カウンターは最終値まで保持されるので、通知間の増分が2だからといって回転が失われたとは限らない。受信間隔だけで物理的な回転間隔を直接計算することにも注意が必要。

## 時刻とrpmの注意点

標準CSCの時刻は1/1024秒単位、16ビットで周回する。標準式は `rpm = 回転増分 × 60 × 1024 / 時刻増分`。[Bluetooth SIG CSC仕様 §3.1.1.2–3](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/CSCS_v1.0/out/en/index-en.html)

最初の2件の変化は、運動前の停止が時刻差に含まれるため除外した。その後の比較は次のとおり。

| 指標 | forward | reverse |
| --- | ---: | ---: |
| PCの受信時刻による経過 | 97.048秒 | 100.980秒 |
| センサー時刻増分の総和（周回補正後） | 194,560 ticks | 202,160 ticks |
| 上記を標準単位で秒へ変換 | 190.000秒 | 197.422秒 |
| センサー秒 / PC秒 | **1.9578倍** | **1.9551倍** |
| Crank標準式rpmの中央値（最初のペア除外） | 64.00rpm | 61.44rpm |
| Crank増分を半分にし、PCの経過で求めた平均 | 62.44rpm | 59.42rpm |

カウンターが約2倍でも、センサー時刻もほぼ2倍に進むため、標準式のrpmはおおむね60前後になる。**累積回転数を2で割ることと、標準式で計算済みのrpmを2で割ることは別。** 後者では約30rpmになり、今回の操作と整合しない。

時計の比率が約1.955〜1.958であることは、2回分の加算に加え、1024Hzではなく1000Hz相当で時刻を生成する仮説とも近い（2×1000/1024≒1.9531）。ただし時計の単位の断定や2.4%の自動補正を決めるには、PC時刻との長時間比較・開始停止の管理が必要。この数値だけから規格違反や正確な内部実装までは決めない。

## Wheelは何を測っているか

全通知でWheelとCrankの最終回転時刻が一致し、各レコードの `Wheel − 3.14 × Crank` はforwardで約−0.48〜+0.64、reverseで約−0.28〜+0.84に収まった。

これだけ強く追従するため、Wheelは同じ入力を固定倍率で変換した値である可能性が高い。実物の車輪・フライホイールを独立に観測したことの証拠にはならない。約3.14という倍率の設計意図も未確認。Wheelから実際の走行速度・距離・ワット数を導かない。

## エクササイズ計測アプリへの反映案

1. 生のWheel / Crankは記録し、運動用の回転数とは表示を分ける。
2. この個体の仮の校正値は「ペダル回転数＝Crank増分÷2」。今後の確認で変更できるようにする。
3. 総回転数・運動時間は停止後も表示を保持する。瞬間rpmの0または未更新状態と別に扱う。
4. 平均rpmは校正した回転数とPC側の運動時間から求める。始動・停止判定のルールを決める。
5. 瞬間rpmは標準式の値と、校正回転数をPC時刻の数秒窓で集計した値を比較し、安定する方式を選ぶ。ペア内の数msを回転間隔として使わない。

今回の表示が確認しづらかった点は、回転の増分を逐次更新する表示と、停止後にrpmを空欄にするUIの影響もある。今回の両ログは最後の変化後も、同じ値の通知を約4秒間受信している。「表示がなくなる＝センサーが即座に通知を止める」とは読み取れない。少なくとも最終累積値はログに残っており、停止後に総回転数を読めるUIにすれば10回単位でも検証しやすくできる。

## 向きを決めるための追加確認

メーカーの指定を特定するには取扱説明書や取り付け写真が必要。今回のログだけなら、**両方とも測定できており、逆向きだけを避ける根拠は見つからない**という判断になる。

測定上の差をさらに確かめるなら、停止後も結果を保持する画面にして、各向きで20回転を低速（約30rpm）・通常（約60rpm）・速め（約90rpm）でそれぞれ2〜3回試す。操作しやすい固定位置のまま、ペダルの目印が同じ位置に戻ることを1回転として数える。これで、方向による低速の検出漏れや速度依存の倍率差を比較しやすい。

この追加試験まで行わなくても、まず現在の向きのまま、倍率を設定できる計測アプリを作るための情報は揃いつつある。
